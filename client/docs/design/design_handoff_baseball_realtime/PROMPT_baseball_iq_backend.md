# Baseball IQ — BACKEND ONLY

**Date:** Sep 8, 2026 · **Scope: server-side only.** No UI work in this handoff.
**Design reference:** `design-so-far.html` in this folder (the five front-end states — open it in a browser) and
`BaseballIQ` inside `LineScoreBand` in `holistic/game-v2.jsx`.
**Do not build any UI from this document.** The client surface is designed and will be ported
separately. What matters here is that the server produce the two payloads below; the front end
already knows what to do with them.

---

## 1. What the feature is, in one paragraph

Baseball IQ is two functions sharing one surface. **Insights** are generated by the server,
unprompted, and pushed to the client as a game progresses. **Questions** are asked by the user
and answered on request. The client shows at most **one** insight at a time, in a single line,
in the sticky score bar. When the server has nothing worth saying, it says nothing and the
surface falls back to an "Ask Baseball IQ" affordance — **silence is a supported, expected,
frequent outcome, not an error.** Build for that: it is cheaper and better to emit nothing than
to emit something obvious.

---

## 2. Delivery: insights ride the existing play feed

**Do not create a push endpoint or a socket channel for insights.** They are properties of a
game's current state, and the client already receives that state on every play update. Add
fields to the existing play-feed payload:

```jsonc
{
  // …existing play update fields, unchanged…
  "iq": {
    "candidates": [                       // 0..3, ALREADY sorted best-first
      {
        "kind": "Leverage",               // enum, see §4
        "score": 0.86,                    // 0..1, the selector's ranking score
        "text": "Bregman has a .318 average with two outs and runners in scoring position — 40 points above his overall mark."
      }
    ],
    "suggested": [                        // 0..3 situational questions, see §5
      "How often does Bregman come through here?",
      "Would that last hit be out in other parks?",
      "When did the Cubs last win from three down?"
    ]
  }
}
```

**`"iq": { "candidates": [], "suggested": [] }` is the normal, correct silence payload.**
Omitting `iq` entirely must be treated identically by the client, so either is acceptable.

### The one hard rule about this payload

`candidates` and `suggested` must be derived from **the same context object**, computed at the
same moment. The client treats them as one signal: a game state that produces no insight is not
allowed to produce suggested questions either. If you generate them in two places, they will
drift, and the user will get questions about a situation the screen is not in.

### Context correctness

The payload must describe **the state of the game at that play update** — not "the game as of
now". This matters because the client replays: the Scout/review view slices the update list to
a marker index and renders that update's `iq` block. A single hard-coded or "latest known"
insight array leaked *"two outs and runners in scoring position"* into a game that had not
started yet, and into a finished one, and named a pitcher who was not in the dataset. If your
generator cannot yet produce a state-accurate block for a given update, emit the empty payload
for it.

---

## 3. The generator

**Input:** the full game context at one play update — score, inning, half, outs, count, base
state, batter, pitcher, both lineups, the play that just happened, the game's play history,
plus season/career splits for the batter and pitcher and the relevant team history.

**Output:** up to three candidates, each scored, sorted best-first.

**Triggers.** Insight generation is *not* limited to between-innings. That gap is simply the
trigger with the most room. Run the generator on at least:

- a scoring play
- a pitching change
- a milestone (career/season round number crossed, no-hitter alive, cycle in progress)
- a leverage-index threshold crossing
- a streak crossing a round number (hits, retired batters, scoreless innings)
- a half-inning gap

**Text requirements.** One sentence. Plain language, no sabermetric shorthand the average fan
would not use out loud. It renders on a **single ellipsised line** in the bar, so front-load the
subject and the point — a sentence whose payoff is in its last six words will be cut off.
Target ≤ 110 characters; anything past ~140 is effectively truncated.

**A candidate must be non-obvious.** "The Cubs are down three runs" is on the scoreboard six
inches away. The bar is worth spending only on something the screen does not already say.

---

## 4. `kind`

A closed enum. It renders as a small uppercase eyebrow, so keep the values short and
fan-legible. Current set, from the design:

| `kind` | Means |
|---|---|
| `Leverage` | This moment matters more than average / how this batter performs in it |
| `Streak` | A run of something, by a player or a team |
| `Rare` | Hasn't happened in a long time, or almost never happens |

Adding a value is a design change — it appears verbatim in the UI. Propose, don't invent.

---

## 5. `suggested`

Up to three questions the user might want to ask **right now**, generated from the same context
as the candidates. They exist because an empty ask box invites nothing.

They must be **situational, not generic** — "How often does Bregman come through here?" rather
than "Show me the box score". Each one, when submitted verbatim to `/iq/query` (§6), must
return a real answer; a suggestion that cannot be answered is worse than no suggestion.

---

## 6. `POST /iq/query`

One endpoint. Free-text question in, answer out.

**Request**

```jsonc
{
  "gameId": "776543",
  "updateIndex": 412,        // WHICH moment the user is asking from — required.
                             // The client may be in review mode at an earlier point,
                             // in which case "the last hit" is NOT the most recent one.
  "question": "Would that last hit be out in other parks?"
}
```

**Response**

```jsonc
{
  "headline": "22 of 30",    // short, mono, usually numeric — the answer in as few chars as possible
  "unit": "parks",           // 1-2 word label rendered beside the headline; optional
  "sub": "Suzuki's single to right field (104.1 mph, 12° launch) clears the wall in 22 of 30 parks. Wrigley's right-field wall is 353 ft at that angle; the shortest is 302 ft.",
  "facts": [                 // 0-3 supporting figures. More than 3 will not fit.
    { "label": "Distance",  "value": "361 ft" },
    { "label": "Exit velo", "value": "104.1 mph" },
    { "label": "Launch",    "value": "12°" }
  ]
}
```

Shape notes the client depends on:

- `headline` is rendered at 30px mono — it is a number or a very short phrase, **not** a sentence.
- `sub` is 1–3 sentences of prose.
- `value` strings arrive **formatted, with units**. The client does no number formatting.
- The client cannot currently render a chart or a long list. If a question needs one, answer in
  prose or decline — do not invent a payload shape for it. Charts and lists are a later design.

**Scope of answerable questions:** this game and its participants, the two teams, and baseball
history/records. Park factors, matchup history, and season/career splits are all in scope.

---

## 7. Park factors — do these as insights too

Park-factor answers ("would that be out elsewhere") are **precomputable per batted ball** from
data you already ingest. Once the computation exists for `/iq/query`, run it on scoring plays
and hard-hit outs and let strong results enter the candidate pool. The user should not have to
know to ask.

---

## 8. Yours to decide — the selector's threshold model

This is deliberately not designed, because it is a server judgement, not a visual one:

- What score constitutes "worthy" — the bar below which you emit nothing.
- **Cadence.** How often an insight may appear. The bar is persistent chrome; a new fact every
  thirty seconds is noise.
- **Repetition memory.** Don't restate a fact, or a near-variant of it, within a game.
- Whether the runners-up or the selector's reasoning ever surface. (Send `score` regardless —
  the client ignores it today, and it is the thing we'll want when tuning.)

---

## 9. Not in scope here

Latency and error states for `/iq/query` are **not designed yet** — deliberately, because their
shape depends on your real round-trip cost. **Report that number when you have it** and we will
design against it. Also out of scope: follow-up questions, chart/list answers, and mobile.

Marker-aware generation for the review view is a follow-up: today the client passes empty
candidates in Scout and pregame. Per §2, if each play update carries its own accurate `iq`
block, review mode gets correct insights for free and that follow-up disappears.

---

## 10. Acceptance

1. Every play update carries an `iq` block (possibly empty) describing **that** update's state.
2. Replaying a finished game update-by-update never shows an insight referencing a player,
   score, or situation not present at that point.
3. Pregame updates carry empty `candidates` and empty `suggested`.
4. `candidates` is sorted best-first and never longer than 3.
5. Every string in `suggested`, submitted verbatim to `/iq/query`, returns a populated answer.
6. `POST /iq/query` with an `updateIndex` earlier than the live one answers **as of that moment**
   ("the last hit" resolves to the last hit before that index).
7. A game state with nothing interesting produces the empty payload rather than a filler fact.
